# Operator-controlled owner recovery

Scope: M01/#55, portable reset semantics with a Node/SQLite operator and a D1 import bridge. The public server exposes reset redemption, never reset issuance. An MCP grant or Fortnox service-account identity cannot issue a recovery code.

For D1, `npm run prepare:product:recovery` reads ignored `.data/product-recovery.json` containing the exact installation `origin`, persistent `ownerId` and owner `email`. `AUTH_SECRET` comes from the private `.env`; a private `secret` field can override it. Run from the repository root, or set `PRODUCT_MIGRATIONS_DIR` to the installed migration directory. The selected D1 database must already have the product migrations.

The Node helper creates an ephemeral in-memory owner projection and invokes the pinned Better Auth 1.7.10 `requestPasswordReset` API. It copies no password, account, session or company data. The library supplies its own opaque token, verification identifier and ten-minute expiry. The helper emits only that verification record as SQL, guarded by the destination installation's active owner ID and matching email. It does not insert or change the destination owner. This avoids handwritten reset-token or password-hashing semantics and requires the native D1 regression when the auth pin/schema changes.

The CLI writes `.data/product-recovery-code.txt` and `.data/product-recovery.sql` with mode 0600 and refuses final-path symlinks. It prints no code, identity or secret. Apply the SQL once to the chosen installation and require exactly one changed row. A different owner/email or an already expired record produces zero changes. Both files carry operator authority: remove them after redemption rather than reimporting a consumed record. Issuance always requires installation/database access; it is not an HTTP or model capability.

The owner opens `/reset-password` and submits the code and new password in a same-origin POST body. The fixed public form does not read tokens from its URL. Better Auth validates expiry, consumes the record once, hashes the new password and revokes admin sessions. The installation owner ID, company handles and connection generations remain unchanged. Existing MCP grants follow their separate revocation policy; changing a password does not broaden them.

Verification uses the built product Worker in actual local workerd/D1: mismatched owner/email and quoted SQL input cause zero inserts; an expired code is rejected; foreign Origin is denied without consuming a valid code; one valid redemption succeeds; replay fails; the old admin cookie is rejected; the new password signs in and reads the same synthetic company; the owner ID remains identical. A separate CLI process test verifies 0600 output and absence of the capability, owner and secret from stdout/stderr. These are synthetic local runtime checks; actual hosted recovery requires a separate owner-operated run.
